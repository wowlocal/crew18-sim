# Журнал экспедиции

Реализация для SwiftUI / iOS 17 без внешних зависимостей и сетевых запросов.

## Архитектура и схема

`GameEngine` снимает значения состояния в точках игровых событий и раз в секунду активного игрового времени. Последовательная цепочка задач передаёт их в `ExpeditionLogger` без ожидания SQLite на MainActor. Actor назначает монотонный `sequenceNumber` отдельно каждой экспедиции. При конкурентных вызовах порядок — порядок приёма actor; для GameEngine сохраняется порядок возникновения событий.

`LogStore` — синхронная обёртка SQLite3, целиком изолированная actor-владельцем. `LogReader` — отдельный actor и отдельное соединение. SQLite работает в WAL, с foreign keys, prepared statements и транзакциями. Файл: Application Support/Expedition/journal.sqlite.

- `expeditions`: id, date, duration, result, cargo, reason.
- `events`: expedition, sequence, category, type, json. Первичный ключ `(expedition, sequence)` исключает повторную вставку; удаление экспедиции каскадно удаляет события.
- JSON события: expeditionId, sequenceNumber, timestamp, schemaVersion=1, category, type, severity, payload. Payload — словарь строк, в том числе числовые значения и версия формата мира v1.
- Reader возвращает события по курсору `after` (sequence), фильтру категории и limit (максимум 1000). Список экспедиций имеет limit/offset. UI подгружает страницы по 200 событий / 30 экспедиций.

## Покрытие

Start/end (completed, gameOver, abandoned), pause/resume, переходы Welcome/Game/Map/Pause/Result и открытие журнала, гаража, отдельного replay; steering не чаще 4 раз/с плюс отпускание; sonar, boost, усиление фар; pickups и black box, изменение цели; armed/exploding mine, столкновение с рифом, damage/поглощение щитом; energy/hull/cargo в snapshots и ключевых событиях; docking; вход в пещеру и завершение босса. Ошибки некорректного steering и недоступных способностей имеют категорию Errors.

Каждое игровое событие также содержит положение, скорость/heading, энергию, корпус, груз/образцы/black box, щит, цель, зону, размеры мира, оставшиеся pickups, фазы/таймеры мин, геометрию рифов и состояние основных способностей/босса. Это позволяет точно восстанавливать дискретное состояние на событии, не ждать следующего периодического snapshot.

## Batching, ошибки и хранение

Запись — каждые 64 события либо через 2 секунды. End выполняет flush немедленно внутри logger. При inactive/background игра ставится на паузу, ожидается передача накопленных событий и выполняется flush под iOS background task. На поверхности также есть доступ к журналу.

Транзакция либо записывает весь batch, либо откатывается. При ошибке очередь сохраняется и повторяется через 2 секунды; ошибка доступна через `lastError` и показывается в журнале. При 512 событиях в очереди новые snapshots пропускаются с увеличением `droppedSnapshots`. Критические и navigation-события не отбрасываются. При постоянной ошибке диска очередь критических событий может расти: абсолютная сохранность при недоступном диске и ограниченная память одновременно невозможны.

При первом открытии writer после запуска незавершённые записи получают `interrupted`; длительность и груз берутся из последнего сохранённого события. Reader сам не объявляет активную игру прерванной. Production использует один shared writer.

После batch удаляются старые завершённые экспедиции: сохраняются последние 50 завершённых записей (активные защищены отдельно), затем старые завершённые игры удаляются до 32 MiB JSON payload. WAL checkpoint и incremental vacuum освобождают страницы; 32 MiB — бюджет содержимого, не строгий размер файла с индексами/страницами. Активная экспедиция не удаляется ради квоты.

## Replay и граф

Replay загружает события страницами через reader. Физика не запускается. Timeline использует активное игровое время; паузы имеют события, но не растягивают запись на реальное время ожидания. Seek двоичным поиском выбирает последнее сохранённое состояние, линейно интерполирует x/y и скорость до следующего. Дискретные поля берутся из предыдущего состояния; через смену зоны интерполяции нет. Canvas показывает лодку, цель, рифы, pickups и мины; рядом отображаются ресурсы и недавние события. Это обзорная карта, а не покадровая копия игрового рендера.

До трёх highlights: blackBox/docking, затем damage/mine, затем pickup/sonar/boost. Минимальное расстояние — max(5 секунд, 8% длительности). Если подходящих событий меньше, маркеров меньше. Маркеры и подписанные кнопки выполняют seek.

User-flow агрегирует fromScreen → toScreen, исключает самопереходы и считает каждое ребро. Граф состоит из подписанных связей со стрелками и счётчиками. Нативные элементы SwiftUI масштабируются с Dynamic Type и сообщают каждую связь VoiceOver. Доступны конкретная экспедиция и все сохранённые игры; удалённые retention-политикой игры не входят в агрегат. Переходы внутри самого просмотрщика (события → граф/replay) не относятся к игровому маршруту.

## Проверка и ограничения

Команда проверки (destination можно заменить своим симулятором):

```sh
xcodebuild -project PodlodkaDive.xcodeproj -scheme PodlodkaDive \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -derivedDataPath /tmp/expedition-build CODE_SIGNING_ALLOWED=NO clean test \
  -only-testing:PodlodkaDiveTests \
  -only-testing:PodlodkaDiveUITests/ExpeditionJournalUITests
git diff --check
```

Unit tests: concurrent stress на 5000 событий, sequence/уникальность, 79 batches, explicit/end/timer flush, повторное открытие/interrupted, rollback, retry без потери критических событий, перегрузка snapshots, пагинация/категории, retention, seek/interpolation/смена зоны/highlights, user-flow. UI test проходит журнал, запись, replay, slider, highlight, play/pause и оба режима графа. GameEngine benchmark выполняет 7200 шагов с логированием (120 секунд игрового времени).

Benchmark измеряет CPU игрового цикла в симуляторе, не GPU/FPS на физическом iPhone. Профилирование Instruments на устройстве не выполнялось. JSON сериализация, SQL и чтение вынесены из MainActor; создание небольшого снимка состояния остаётся на MainActor. Полный replay загружается в память; для очень длинной активной игры потребуется оконное чтение.

При принудительном убийстве процесса возможна потеря ещё не зафиксированного batch (обычно до 2 секунд); background flush не гарантирован при crash/force quit. Версия схемы записана, но миграция будущих форматов ещё не нужна. Нет экспорта, облачной синхронизации и побитового воспроизведения визуальных эффектов.
